Part C

Database provider

already live Supabase (Postgres, hosted) — the free tier, no card.

This was already the project's database before this module — used for every coach-auth and dashboard flow tested this session. No new provider was needed; Supabase was already the right call here (Postgres, matches the module, free, has a table viewer).

One thing only you can grab: the Table Editor screenshot needs your own Supabase login — open the dashboard, wake the project if it's paused from inactivity, open Table Editor, screenshot. Not something I can do without your credentials, and I don't ask for those.
Part D

Schema & connection

1. Schema from the ERD

already built Matches the ERD above exactly — it's what the ERD was derived from.

Lives at backend/src/db/schema.sql (not a fresh db/schema.sql — the project already tracks its schema at that path with its own history in notes/decisions.md, so a second copy would just create the stale-duplicate problem that decision already ruled out). Every table has a UUID primary key (default gen_random_uuid()), created_at, and foreign keys on the "many" side — confirmed against the table above. Run via Supabase → SQL Editor → paste → Run.

2. Project connected to it

already done Real credentials gitignored, example file committed empty, both ends read from env vars.
  • backend/.env — real values, confirmed not committed (checked git ls-files directly)
  • backend/.env.example — same keys (SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, …), all empty, committed
  • frontend/.env.example — VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, empty, committed
  • .gitignore — contains .env
  • backend/src/config/supabaseClient.js — backend db client, service-role, reads from env
  • frontend/src/lib/supabaseClient.js — frontend db client, anon key, reads from env

Both clients fail soft on a missing key (a placeholder host, not a crash at boot) — deliberate, so the app still renders locally before real credentials exist, per plan/19's pilot timeline.
