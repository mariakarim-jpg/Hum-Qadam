§2

The one bug — before / after

Direct navigation to any dashboard route returned a raw Vercel 404. A single-page React app needs a rewrite rule telling Vercel to serve index.html for any path that isn't a real static file — the backend already had one; the frontend never did.

Before

Navigating straight to /teachers/<id>, refreshing on any non-root page, or opening a shared link all returned Vercel's own 404: NOT_FOUND — the React app never loaded at all, and a signed-in coach lost their session outright.

After

The same direct link now loads the real app shell — sidebar, nav, signed-in coach's email, sign out — every time. A made-up teacher ID still fails, but now correctly, inside the app, as a data-lookup error rather than a page that never loaded.

// frontend/vercel.json — added
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}

§4

Reflection

What testing actually found

Four real bugs — none of them things a code read would have caught. Two were about what happens when something goes wrong (an expired login link, a failed confirmation email) rather than the happy path, and one only showed up because I tried navigating directly to a URL instead of always clicking through from the homepage. The app "worked" every time I used it the way I built it to be used, and broke the moment I used it the way a real teacher-coach actually would — refreshing mid-session, sharing a link, opening an old email days later.

What I'd do differently earlier

I'd have caught the direct-navigation 404 and the silent email failures much sooner by testing the live deployment from day one instead of trusting that "it works locally" would carry over. Vercel's routing and Supabase's email rate limits only exist in production — no amount of careful local testing surfaces them.

What I'm taking forward

"Does the code look right" and "does it actually work" are different questions, and only one of them protects a teacher-coach from a broken screen at 6am. Before the next deploy, every new flow gets an unhappy-path check, not just the happy path — and it gets tested against the real deployed URL, not just localhost.
